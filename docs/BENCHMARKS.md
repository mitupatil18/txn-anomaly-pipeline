## How to run

```bash
docker compose up -d --build          # the stack must be buildable; the script manages the rest
python scripts/benchmark.py --messages 200000 --runs 3 --experiments A B C D E
python scripts/benchmark.py --experiments F --runs 3   # optional: partition count
python scripts/benchmark.py --render-only              # regenerate the table from benchmarks/results.json
```

Raw per-run data is written to `benchmarks/results.json`.

## Method

For each run the script wipes PostgreSQL, Redis and both topics, recreates the topics, pre-loads
`N` messages with the simulator (`--count N --rate 0 --seed 42 --accounts 2000`) **while no consumer
is running**, then starts `K` consumers with `BATCH_SIZE=b` and waits until `N` rows are in
PostgreSQL.

* **Throughput** = `N / (max(processed_at) - min(processed_at))`: the time the consumers needed to
  drain the backlog, excluding container start-up.
* **Processing latency** = `txn_processing_seconds` p95 from Prometheus (per message; batch time
  divided by batch size).
* **End-to-end latency** = `processed_at - event_time` from PostgreSQL. Because the backlog is
  pre-loaded, this number is dominated by queueing time and is a *drain* metric, not the latency
  you would see at a sustainable arrival rate. Use the Grafana dashboard under `make load` for that.
* Each experiment is run several times; the table shows the median.

| ID | Configuration | Purpose |
|---|---|---|
| A | 1 consumer, `BATCH_SIZE=1` | baseline |
| B | 1 consumer, `BATCH_SIZE=200` | effect of batching |
| C | 3 consumers, best batch | horizontal scaling |
| D | 6 consumers, best batch | scaling up to the partition count |
| E | 8 consumers, best batch | more consumers than partitions: 2 sit idle |
| F | 6 consumers, 3 partitions (optional) | effect of partition count |
