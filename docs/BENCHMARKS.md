# Benchmarks

Every number in this file is produced by `scripts/benchmark.py`; nothing here is estimated.
Raw per-run data (including every individual run) is in `benchmarks/results.json`.
Experiments A to F were run 3 times each.

## How to run

```bash
docker compose up -d --build          # the stack must be buildable; the script manages the rest
python scripts/benchmark.py --messages 200000 --baseline-messages 20000 --runs 3 --experiments A B C D E
python scripts/benchmark.py --experiments F --runs 3   # partition count (needs the topic recreated with 3 partitions; the script does this)
python scripts/benchmark.py --render-only              # regenerate the table from benchmarks/results.json
```

Experiment A was run with **20,000** messages instead of 200,000 because at about 90 msg/s a
200,000-message run would take ~40 minutes; throughput is a rate, so the comparison still holds,
but note the different `N`.

## Method

For each run the script wipes PostgreSQL, Redis and both topics, recreates the topics, pre-loads
`N` messages with the simulator (`--count N --rate 0 --seed 42 --accounts 2000`) **while no consumer
is running**, then starts `K` consumers with `BATCH_SIZE=b` and waits until `N` rows are in
PostgreSQL.

* **Throughput** = `N / (max(processed_at) - min(processed_at))`: the time the consumers needed to
  drain the backlog, excluding container start-up.
* **Processing latency** = `txn_processing_seconds` p95 from Prometheus (per message; batch time
  divided by batch size).
* **End-to-end latency** = `processed_at - event_time` from PostgreSQL. Because the backlog is
  pre-loaded, this number is dominated by queueing time and is a *drain* metric, not the latency
  you would see at a sustainable arrival rate. Use the Grafana dashboard under `make load` for that.
* Each experiment is run several times; the table shows the median.

| ID | Configuration | Purpose |
|---|---|---|
| A | 1 consumer, `BATCH_SIZE=1` | baseline |
| B | 1 consumer, `BATCH_SIZE=200` | effect of batching |
| C | 3 consumers, best batch | horizontal scaling |
| D | 6 consumers, best batch | scaling up to the partition count |
| E | 8 consumers, best batch | more consumers than partitions: 2 sit idle |
| F | 6 consumers, 3 partitions | effect of partition count |

## Analysis

Individual runs (msg/s): A 82 / 86 / 96, B 972 / 992 / 628, C 1,512 / 1,618 / 1,789,
D 2,038 / 1,980 / 1,941, E 2,112 / 2,934 / 1,987, F 1,504 / 1,340 / 1,937. The machine also ran Kafka, Postgres, Redis,
Prometheus and Grafana in one Docker VM, so run-to-run noise is large (see B run 3 and E run 2).

* **Batching is the big win: A to B is ~11x** (86 to 972 msg/s, medians). With `BATCH_SIZE=1` every
  message costs a database transaction commit (an fsync) and a synchronous Kafka offset commit; at
  `BATCH_SIZE=200` both are amortised over the batch, and the Redis reads/writes become one
  pipelined round trip per batch. Per-message processing time fell from a p95 of 23.7 ms to 2.35 ms.
* **Horizontal scaling helps, but sub-linearly:** 1 to 3 consumers gave ~1.7x, 1 to 6 consumers ~2.0x
  (972, 1,618, 1,980 msg/s). Perfect scaling would have been 3x and 6x. Per-message p95 processing time
  rises from 2.35 ms (B) to 4.83 ms (D) as consumers are added, which points to contention on a
  shared resource rather than to the consumers themselves.
* **Likely bottleneck: PostgreSQL (and the shared Docker VM).** `docker stats` showed Postgres at about
  one full core in B to D (peak 96 to 114%, 208% in E) while Redis never exceeded 34%, so Redis was not
  the limit. All services shared the same 14-CPU Docker VM, including Kafka (up to ~260 to 300%), so
  part of the ceiling is the test machine itself. I did not isolate the database further (for example
  by testing with `synchronous_commit=off` or a tuned Postgres), so treat "Postgres" as the most
  likely explanation, not a proven one.
* **E (8 consumers, 6 partitions):** the median (2,112 msg/s) is within the spread of D. Run 2 was
  an outlier (2,934); runs 1 and 3 match D. Kafka assigns a partition to at most one consumer of a
  group, so the two extra consumers sit idle and cannot add throughput; they are only useful as
  hot standbys that take over on failure. With this noise the data cannot show any difference
  between D and E.
* **F (6 consumers, 3 partitions):** median 1,504 msg/s versus 1,980 for D (same consumers, 6
  partitions), about 24% lower. Only 3 of the 6 consumers receive a partition, so F behaves like C
  (3 active consumers, 1,618 msg/s): the two medians are within the noise of each other. Run 3 (1,937)
  overlaps D's range, so with only 3 runs the size of the gap is uncertain; the direction
  (fewer partitions caps parallelism) is what the design predicts. The partition count is the upper
  bound on useful consumers, and it is hard to raise later without disturbing key-to-partition mapping.
* **End-to-end latency here is drain time** (see Method): p99 is roughly equal to the drain time because
  the backlog was pre-loaded. It says how long the last message waited, not the latency at a
  sustainable load. Note that the default `BATCH_SIZE=1` only sustains roughly 90 msg/s here, so
  a 400 msg/s `make load` builds lag under that setting (see the screenshot in the README); with
  `BATCH_SIZE=200` the same load is absorbed and lag returns to zero.

Relative improvements are the point; absolute numbers depend on the machine.
